# Master Data — Customer Master

The "Customer Master" screen under Master Data > System Management
(`/master-data/system-management/customers`). Covers creating, editing,
listing/searching, and deactivating a Customer — the buyers/brands that
place orders against this factory. No automation exists for this module
yet, so this file uses the simple 4-column format (no ClickUp/Automated/
Verified columns).

## Notes for whoever picks this up next

All findings below were confirmed live against `https://dev.flooros.app` on
2026-10-06 using a real authenticated session (`.auth/master-data.json`) and
throwaway records prefixed `TC-Customer-...` — this module had **zero**
existing documentation or automation in this repo before this file. This is
a large, busy shared dev dataset (1186+ customers at the time of writing);
counts quoted anywhere in this file are a point-in-time snapshot, not a
fixed expectation.

- **List**: heading "Customer Master" (`level=1`), status tabs All / Draft /
  Approved / Inactive / Rejected (each with a live count), search ("Search
  by code, name, contact, email…"), Filters/Refresh/Export CSV/Toggle cell
  filters/Configure columns/Best-fit columns, 3 layout modes, a "New
  Customer" button (capital C, matching Company Master's "New Company" —
  differs from Departments/Sites' lowercase convention). Table columns:
  Customer Code, Customer Name, City, Country, Email, Buyer Code, Status.
- **Two extra dashboard-style regions sit above the table**, not seen on
  Company Master: "Masters needing review" (lists Draft customers awaiting
  Master Approval, each with Review/Reject/Make active actions) and
  "Rejected — needs revision" (customers sent back by Master Approval, with
  an "Acknowledge & withdraw" action). These are a real approval workflow,
  not yet exercised end-to-end by this file's test cases — see "Not covered"
  below.
- **Create form** fields, exactly as marked live with `*`: Customer Code
  (disabled, auto-generated), Prefix ID\*, Customer Name\*, Contact Person,
  Email, Website, Phone 1, Buyer Code, Fax, Address Line 1, Address Line 2,
  City, State/Province, Postal Code, Country\*, Currency\*, Payment Method
  (defaults "— None —"), Credit Terms (defaults "— None —"), Active
  (checkbox, defaults checked). A "Brands" tab sits alongside "General" —
  gated behind an initial save (see TC:5). **The four starred fields are
  genuinely required** — submitting empty shows inline "Required" under all
  four at once, confirmed live, no Sites-style gap between what looks
  required and what's enforced.
- **Clicking a row opens straight into the Edit Customer form** — there is
  no separate read-only detail view, same shape as Company Master. URL
  pattern: `?create=true` for new (no dedicated `/new` route).
- **Status model is richer than Active/Inactive**: Draft, Approved,
  Inactive, Rejected. **New customers created with only the required fields
  landed directly in "Approved" status, not "Draft"** on this dev
  environment/user — confirmed live by creating a real customer and reading
  its row status immediately after. This suggests the logged-in test user's
  default Company does not have "Master Data Approval Required" enabled
  (see Company Master's own file for that switch) — not independently
  verified which Company this user's new Customers are scoped under.
- **Confirmed-live, surprising: duplicate Prefix ID is allowed.** Two
  different customers were created back-to-back reusing the identical
  Prefix ID value and both saved successfully with their own distinct,
  auto-generated Customer Codes. This is the **opposite** of Company
  Master's Company Code, which does block duplicates. Don't assume Prefix
  ID is a uniqueness-enforced business key anywhere else in the app without
  re-checking.
- **Email format validation is native-browser, not app-level.** Entering
  `not-an-email` and submitting produces no toast and no inline "Enter a
  valid email" message in the DOM/ARIA tree — the browser's own
  `type="email"` constraint silently blocks the submit (confirmed via
  `el.validity.typeMismatch === true` and reading `el.validationMessage`
  directly). Worth knowing before building a Playwright assertion around an
  "Invalid email" inline error that will never actually appear.
- **Exact success toast text, confirmed live:**
  - Create: `Customer <CODE> created.` (the auto-generated Customer Code is
    interpolated directly into the toast, e.g. `Customer CTC0001354
    created.` — don't match on a static string).
  - Edit/Save: `Customer updated.`
  - Deactivate: `Customer deactivated.`
- **Same reactivation bug as Company Master, confirmed live again here**:
  the "Deactivate" button at the top of Edit Customer never relabels to
  "Activate" once the record is already Inactive; reactivating only works
  by checking the in-form "Active" checkbox and clicking "Save changes".
  Documented independently in both files since it's the same underlying
  component/pattern reused across at least two Master Data screens, not a
  one-off.
- Same dev OIDC redirect timing quirk and `gotoAuthenticated()` requirement
  as every other Master Data screen (see
  `agent-notes/master-data-module.md`).
- **Not covered in this pass**: the Draft/Approved/Rejected Master Approval
  workflow itself (Review/Reject/Make active/Acknowledge & withdraw
  actions), the Brands sub-tab's own Add/Edit/Delete flow, Website/Phone
  field format validation (if any), Payment Method/Credit Terms dropdown
  option lists, Filters rule-builder UI, Export CSV content, and bulk
  row-selection actions.
