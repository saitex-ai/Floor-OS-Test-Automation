# Planning — Operation Allowances (Create / Edit)

- **User Story:** As a Planner, I want to record an operation's allowances (fatigue, material handling, machine interruption …) — added, never compounded — so standard minutes include them.
- **Test-case set:** [ClickUp — Planning -Sprint -2 - Operations and Allowance](https://app.clickup.com/t/z941abv8mt) (one subtask per TC, in "Test Cases and Runs").
- **Automated in:** [`tests/regression/planning/08-operation-allowances.spec.ts`](../../tests/regression/planning/08-operation-allowances.spec.ts) — 14 cases.
- **Page objects:** [`operation-detail.page.ts`](../../src/pages/planning/operation-detail.page.ts), [`allowance-form.page.ts`](../../src/pages/planning/allowance-form.page.ts) (fixtures `operationDetailPage`, `allowanceFormPage`)
- **Latest run:** dev, 2026-10-22, as `alice` (Admin); permission cases as carol (read-only) and dave (no access); 1 worker — 14 pass.

Allowances live on an operation's detail page: "New allowance" and a row's "Edit" replace the Allowances grid with the form on the same URL. Types are offered as "<type> · default N.NN%"; an off-machine operation is offered two (Human motion fatigue, Material handling). Typing a percentage away from the default flips "Differs from the allowance type default" on, which makes "Why the default was not used" required.

**Test data:** every record this suite creates carries "QA-AUTO" — in its name (operations, work centres), a "QA-AUTO" system link under Asset register & telemetry (machines have no name), or its Why (maintenance windows) — so it can be found and deleted from the backend. The suite never edits seed records. When a spec file finishes, its `afterAll` retires the operations, work centres and machines it created (they can't be deleted) — see `tests/regression/planning/support/cleanup.ts` and `test-data.ts`. Since the 2026-10-16 dev deploy, dev generates activity, recipe, operation, work-centre and machine codes (ACT-0001…, RCP-0001…, OP-0001…, WC-0001…, MC-0001…): each such record carries a run-unique tag in its name (a machine: in its QA-AUTO system link), the suite reads the generated code back after saving, and cleanup finds the record by that tag. Difficulty-grade codes are still typed (`QG<run><n>`).

## Notes for whoever picks this up next

- Lists are the shared Master Data grid (`MasterDataListPage`): `expectLoaded()` waits past the skeleton rows; search / filters apply after a debounce, so assert with `expect.poll` / `expectEveryRowMatches()`.
- Permission cases run as the optional `PLANNING_READONLY_*` / `PLANNING_NOACCESS_*` logins (see `.env.example`), each logged in once per worker (`personas` fixture), and skip without them. Where a read-only user is still offered an enabled control (ClickUp z941abybge), the case drives it and checks the write is refused.
- A row's icon-only "Edit" needs `dispatchEvent('click')` — its `<td>` intercepts a normal click.
- The heading reads "Allowances (0)" until the rows load: use `expectAllowanceCount()`, never a one-off read. For the same reason a count of 0 can't prove nothing was saved: the cancel / blocked cases (TC-COA-02, TC-COA-06) add an anchor row first, then check the count is 1 and the cancelled type has no row.
- Allowances can't be deleted or switched off in the UI (the edit form has no Active switch or delete, checked 2026-10-14), so they stay on their QA-AUTO operation, which cleanup retires.
- Seed data: TC-COA-05 relies on an off-machine operation being offered exactly two allowance types, "Human motion fatigue" and "Material handling" (no "Machine interruption").
