# Planning — Maintenance Windows (Add / Edit)

- **User Story:** As a Planner, I want to record when a machine is unavailable — planned maintenance or an unplanned stoppage — so capacity and the conflict engine account for it.
- **Test-case set:** [ClickUp — Planning -Sprint-2 - Machine and maintenance](https://app.clickup.com/t/z941abv8py) (one subtask per TC, in "Test Cases and Runs").
- **Automated in:** [`tests/regression/planning/11-maintenance-windows.spec.ts`](../../tests/regression/planning/11-maintenance-windows.spec.ts) — 12 cases.
- **Page objects:** [`machine-detail.page.ts`](../../src/pages/planning/machine-detail.page.ts), [`maintenance-window-form.page.ts`](../../src/pages/planning/maintenance-window-form.page.ts), date picker [`date-picker.ts`](../../src/pages/planning/date-picker.ts) (fixtures `machineDetailPage`, `maintenanceWindowFormPage`)
- **Latest run:** dev, 2026-10-30, as `alice` (Admin); permission cases as carol (read-only) and dave (no access); 2 workers — 12 pass.

Windows belong to a machine. Since the 2026-10-28 dev deploy the create and edit forms are two steps (step 1's "Save & continue" saves, Done opens the detail page), and windows are rows of an inline table on step 2 of Edit machine: the add row ("Add maintenance window"; its ✕ Clear discards what was typed), and a saved row's "Edit maintenance window" with Save / Cancel on the row. Each row saves on its own. The detail page shows the table read-only, and Done / Cancel refuse to leave while the add row holds input. Kind and Window start are required; a blank Window end is a stoppage that is still open.

**Test data:** every record this suite creates carries "QA-AUTO" — in its name (operations, work centres), a "QA-AUTO" system link under Asset register & telemetry (machines have no name), or its Why (maintenance windows) — so it can be found and deleted from the backend. The suite never edits seed records. When a spec file finishes, its `afterAll` retires the operations, work centres and machines it created (they can't be deleted) — see `tests/regression/planning/support/cleanup.ts` and `test-data.ts`. Since the 2026-10-16 dev deploy, dev generates activity, recipe, operation, work-centre and machine codes (ACT-0001…, RCP-0001…, OP-0001…, WC-0001…, MC-0001…): each such record carries a run-unique tag in its name (a machine: in its QA-AUTO system link), the suite reads the generated code back after saving, and cleanup finds the record by that tag. Difficulty-grade codes are still typed (`QG<run><n>`).

## Notes for whoever picks this up next

- Lists are the shared Master Data grid (`MasterDataListPage`): `expectLoaded()` waits past the skeleton rows; search / filters apply after a debounce, so assert with `expect.poll` / `expectEveryRowMatches()`.
- Permission cases run as the optional `PLANNING_READONLY_*` / `PLANNING_NOACCESS_*` logins (see `.env.example`), each logged in once per worker (`personas` fixture), and skip without them. Where a read-only user is still offered an enabled control (ClickUp z941abybge), the case drives it and checks the write is refused.
- Window start / end are date-time pickers: today, then the hour and minute buttons (hours 00–23 then minutes 00–59 in one "Pick time" group), then Done. A set field's trigger reads "<value> Clear date and time".
- A row's icon-only "Edit" needs `dispatchEvent('click')`, as on allowances.
- Windows have no code, so cleanup handles them through their machine: before retiring a QA-AUTO machine it switches each still-active window's "Active" off (the form calls it the soft-delete flag).
