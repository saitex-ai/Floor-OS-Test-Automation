# Planning — Generic Approval Workflow (Policies / Inbox / Request lifecycle)

- **User Story:** As an admin I set up approval policies (who approves what, in how many levels), and as a Planner I send records for approval and approvers decide them in an Inbox.
- **Test-case set:** [ClickUp — Planning - Generic Approval Workflow](https://app.clickup.com/t/z941abyu87) (one subtask per TC, in "Test Cases and Runs"); story [Setup Generic Approval workflow](https://app.clickup.com/t/z941abvzym).
- **Automated in:** [`tests/regression/planning/22-generic-approval.spec.ts`](../../tests/regression/planning/22-generic-approval.spec.ts) — 76 cases.
- **Page objects:** [`approval-policies.page.ts`](../../src/pages/planning/approval-policies.page.ts), [`approval-policy-form.page.ts`](../../src/pages/planning/approval-policy-form.page.ts), [`approvals-inbox.page.ts`](../../src/pages/planning/approvals-inbox.page.ts), [`approval-request.page.ts`](../../src/pages/planning/approval-request.page.ts), [`approval-panel.page.ts`](../../src/pages/planning/approval-panel.page.ts).
- **Routes:** policies at `/approvals/policies`, Inbox at `/approvals` (older notes say `/admin/approvals`).

**Test data:** every policy and activity/recipe this suite creates carries "QA-AUTO — generic-approval test data (pw-hybrid-framework). Safe to delete.". Approval policies are shared state: the suite only activates its own policies, only while a send is in flight, and switches them off again in the same test (and in afterAll, which throws if one stays on). The first worker of every run also switches off any of the suite's own policies a killed run left active. It never edits or deactivates a policy it did not create. TC-XAP-05 approves a QA-AUTO recipe through the environment's own "Recipe approvals" policy (which notifies its real approvers); the recipe becomes Active and cleanup retires it.

## Notes for whoever picks this up next

- The second approver is the `PLANNING_READONLY_USER_<ENV>` login (its display name is read from its user menu at run time; no name is written into the suite). Cases that need it or act as it skip with that login's message when it isn't set; the others (the pending-request cases on one Alice-approved request, TC-XAP-10, TC-XAP-13, TC-XAP-24, TC-EAP-05) run on the main Planning login alone.
- TC-XAP-13 and TC-EAP-05 skip only when a _real_ (non-QA-AUTO) active planning · activity policy is in force; a QA-AUTO policy still active fails them (a leak).
- Policies are shared across suites: an active policy changes how Activities/Recipes save everywhere. Keep `sendUnder` (activate → send → deactivate in `finally`) for any new case.
- The approval screens build rows from adjacent spans; read them with `spacedText` / `expectSpacedText` (the level badge "L" "1" is normalised to "L1").
- TC-XAP-22 (send-back and comment thread) is skipped: not built yet on dev/uat; it has no ClickUp subtask.
- TC-XAP-18: only the "calendar None" half is automated; the business-hours half depends on the hour the case runs.
- TC-XAP-04: on dev a reader who isn't on the chain is not shown the "Approval chain" block on the activity page; the case text expects it. Not asserted either way.
- TC-XAP-15's ClickUp item (z941ac28wp) is an open question for the PO, not a confirmed bug; its `knownBug` sits after the steps that work and the title needs PO sign-off if dev's behaviour is accepted.
- TC-XAP-09 and TC-XAP-15 assert the specified behaviour and fail on dev today (candidate product bugs: Self-approval Blocked still seats the submitter; on an "Everyone must approve" level the submitter's single approval completes the level "as administrator"). See the task report.
- The Inbox's Filters panel button is "Apply filters" (the Planning lists say "Apply") and the panel closes itself on apply.
