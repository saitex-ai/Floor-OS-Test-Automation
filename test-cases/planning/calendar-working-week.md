The working week is the "Default working week" card on a calendar's detail page: one line per weekday × shift that runs. Since the 2026-10-28 dev deploy the create and edit forms are two steps (step 1's "Save & continue" saves, Done opens the detail page), and lines (Working week tab) are rows of an inline table on step 2 of Edit calendar: the add row ("Add working-week line"; its ✕ Clear discards what was typed), and a saved row's "Edit working-week line" with Save / Cancel on the row. Each row saves on its own. The detail page shows the table read-only, and Done / Cancel refuse to leave while the add row holds input.

**Test data:** every record this suite creates carries "QA-AUTO" in its name, label or description, so it can be found and deleted from the backend. The suite never edits seed records. When a spec file finishes, its `afterAll` retires what it created (these masters can't be deleted) — see `tests/regression/planning/support/cleanup.ts` and `test-data.ts`. The suite builds two QA calendars: one with Mon A, Tue A, Tue NIGHT and Sat SAT_AM lines, and one with a single Fri B line.

## Notes for whoever picks this up next

- Lists are the shared Master Data grid (`MasterDataListPage`): `expectLoaded()` waits past the skeleton rows; search / filters apply after a debounce, so assert with `expect.poll` / `expectEveryRowMatches()`. Header text carries the sort arrows (↑ ⇅) — strip them before comparing.
- Permission cases run as the optional `PLANNING_READONLY_*` / `PLANNING_NOACCESS_*` logins (see `.env.example`), each logged in once per worker (`personas` fixture), and skip without them. Where a read-only user is still offered an enabled control, the case drives it and checks the write is refused.
- Success toasts fade after a few seconds: `submitExpectingToast()` checks them straight after the click. An open modal hides the grid behind it from the accessibility tree, so read a row before opening its dialog.
