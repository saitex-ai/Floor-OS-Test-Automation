# Planning — Machines (Create / Edit / List)

- **User Story:** As a Planner, I want to register machines with their class, work centre and status so capacity and scheduling know what is available.
- **Test-case set:** [ClickUp — Planning -Sprint-2 - Machine and maintenance](https://app.clickup.com/t/z941abv8py) (one subtask per TC, in "Test Cases and Runs").
- **Automated in:** [`tests/regression/planning/10-machines.spec.ts`](../../tests/regression/planning/10-machines.spec.ts) — 22 cases.
- **Page objects:** [`machines-list.page.ts`](../../src/pages/planning/machines-list.page.ts), [`machine-form.page.ts`](../../src/pages/planning/machine-form.page.ts), [`machine-detail.page.ts`](../../src/pages/planning/machine-detail.page.ts), shared grid [`master-data-list.page.ts`](../../src/pages/planning/master-data-list.page.ts) (fixtures `machinesListPage`, `machineFormPage`, `machineDetailPage`)
- **Latest run:** dev, 2026-10-22, as `alice` (Admin); permission cases as carol (read-only) and dave (no access); 1 worker — 22 pass.

Machines are at `/planning/master-data/machines` (nav tile "Machines & maintenance"); detail and edit pages use the record's uuid. A machine has no name, so a system link (System "QA-AUTO", Identifier "<code> — Planning regression test data …") carries the test-data marker. **The 2026-10-14 dev deploy replaced the free-text "Machine class" with a "Machine type" picker** (the Machine type master, e.g. "BTK · Bartack", no empty choice); every QA machine is a BTK, a type no seed machine uses. The cases below that used the class are adjusted to the type. Version / Effective from / Effective to removed on request — [Demo Feedback](https://app.clickup.com/t/90181912927/z941abwdad) (implemented 2026-09-25).

**Test data:** every record this suite creates carries "QA-AUTO" — in its name (operations, work centres), a "QA-AUTO" system link under Asset register & telemetry (machines have no name), or its Why (maintenance windows) — so it can be found and deleted from the backend. The suite never edits seed records. When a spec file finishes, its `afterAll` retires the operations, work centres and machines it created (they can't be deleted) — see `tests/regression/planning/support/cleanup.ts` and `test-data.ts`. Since the 2026-10-16 dev deploy, dev generates activity, recipe, operation, work-centre and machine codes (ACT-0001…, RCP-0001…, OP-0001…, WC-0001…, MC-0001…): each such record carries a run-unique tag in its name (a machine: in its QA-AUTO system link), the suite reads the generated code back after saving, and cleanup finds the record by that tag. Difficulty-grade codes are still typed (`QG<run><n>`).

## Notes for whoever picks this up next

- Lists are the shared Master Data grid (`MasterDataListPage`): `expectLoaded()` waits past the skeleton rows; search / filters apply after a debounce, so assert with `expect.poll` / `expectEveryRowMatches()`.
- Permission cases run as the optional `PLANNING_READONLY_*` / `PLANNING_NOACCESS_*` logins (see `.env.example`), each logged in once per worker (`personas` fixture), and skip without them. Where a read-only user is still offered an enabled control (ClickUp z941abybge), the case drives it and checks the write is refused.
- "In service since" is a date picker ("Pick date" → today).
- The smoke test still uses `fillRequired()` / `create()` / `expectCreatedSuccessfully()`; the regression suite uses `submitCreate()`.
