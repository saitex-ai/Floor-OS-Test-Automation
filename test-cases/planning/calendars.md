Calendars (`/planning/master-data/calendars`) create and edit on their own pages (`/calendars/new`, `/calendars/<CODE>/edit`). Calendar entries (holidays and other dated exceptions) live on the calendar's detail page: "New calendar entry" and a row's Edit replace the entries grid with the form on the same URL.

**Test data:** every record this suite creates carries "QA-AUTO" in its name, label or description, so it can be found and deleted from the backend. The suite never edits seed records. When a spec file finishes, its `afterAll` retires what it created (these masters can't be deleted) — see `tests/regression/planning/support/cleanup.ts` and `test-data.ts`. Calendar codes are `QA-CAL…`; entries carry "QA-AUTO" in their Why.

## Notes for whoever picks this up next

- Lists are the shared Master Data grid (`MasterDataListPage`): `expectLoaded()` waits past the skeleton rows; search / filters apply after a debounce, so assert with `expect.poll` / `expectEveryRowMatches()`. Header text carries the sort arrows (↑ ⇅) — strip them before comparing.
- Permission cases run as the optional `PLANNING_READONLY_*` / `PLANNING_NOACCESS_*` logins (see `.env.example`), each logged in once per worker (`personas` fixture), and skip without them. Where a read-only user is still offered an enabled control, the case drives it and checks the write is refused.
- Success toasts fade after a few seconds: `submitExpectingToast()` checks them straight after the click. An open modal hides the grid behind it from the accessibility tree, so read a row before opening its dialog.
- Inherits from picks the option that starts `CODE ·`; Time zone is a type-ahead (type the last segment, e.g. "Kolkata").
- Entry Date is a date picker: `pickDayOfShownMonth()` reads the grid's month label ("October 2026") and clicks the day by its full accessible name.
