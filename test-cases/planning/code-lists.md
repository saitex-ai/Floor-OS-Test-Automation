Code Lists (`/planning/master-data/code-lists`) lists the shared lookup tables; there is no create action for a list itself. A row opens that list's values (`/code-lists/<table>`). Values are added and edited in a modal over the values grid: a row click opens a read-only view, and its Edit turns it into the form. Values can't be deleted — "In use" off retires them.

**Test data:** every record this suite creates carries "QA-AUTO" in its name, label or description, so it can be found and deleted from the backend. The suite never edits seed records. When a spec file finishes, its `afterAll` retires what it created (these masters can't be deleted) — see `tests/regression/planning/support/cleanup.ts` and `test-data.ts`. Values are added to two lists only, `delay_owner` (A) and `severity` (B); value codes are generated lower case (`qa_auto_…`).

## Notes for whoever picks this up next

- Lists are the shared Master Data grid (`MasterDataListPage`): `expectLoaded()` waits past the skeleton rows; search / filters apply after a debounce, so assert with `expect.poll` / `expectEveryRowMatches()`. Header text carries the sort arrows (↑ ⇅) — strip them before comparing.
- Permission cases run as the optional `PLANNING_READONLY_*` / `PLANNING_NOACCESS_*` logins (see `.env.example`), each logged in once per worker (`personas` fixture), and skip without them. Where a read-only user is still offered an enabled control, the case drives it and checks the write is refused.
- Success toasts fade after a few seconds: `submitExpectingToast()` checks them straight after the click. An open modal hides the grid behind it from the accessibility tree, so read a row before opening its dialog.
- The value dialog's Close button is the last one in the dialog (the first is the header's ×).
- Display order is a number input: its error message sits two levels up from the input (`fieldAlert(control, 2)`).
