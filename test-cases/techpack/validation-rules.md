# Techpack — Validation Rules

- **User Story:** As a Techpack admin, I want to define and manage validation rules — global or
  scoped to a specific Customer — that automatically check techpack submissions against required
  attributes (labels, hangtags, interlining colour, trims, etc.) at a given Severity, so
  customer-specific compliance requirements are enforced before a techpack is approved.
- **Test-case set:** not yet created in ClickUp (no ClickUp task exists for this story at time of
  writing — the "ClickUp" column below is left blank rather than filled with placeholder links).
  A real bug against this screen already exists, filed separately:
  [z941abxb4p — Saving a validation rule without changes still increments its version](https://app.clickup.com/t/z941abxb4p).
- **Automated in:** [`tests/regression/techpack/06-validation-rules.spec.ts`](../../tests/regression/techpack/06-validation-rules.spec.ts)
  (2026-10-01). 28 cases, all real `test()` blocks (TC:27 was removed on 2026-10-05, see notes).
  TC:26/TC:28/TC:29 need a second, non-admin login (`TECHPACK_SECOND_USER_<ENV>` /
  `TECHPACK_SECOND_PASSWORD_<ENV>`, e.g. `bob` on dev) and skip when it isn't set.
- **Page object:** [`src/pages/techpack/validation-rules.page.ts`](../../src/pages/techpack/validation-rules.page.ts) +
  [`src/locators/techpack/validation-rules.locators.ts`](../../src/locators/techpack/validation-rules.locators.ts)
  (fixture `validationRulesPage`).

The screen lives at **`/techpacks/admin/validation-rules`**, reached via the Techpack module's own
left-nav "WORKSPACE" section (a link labelled "Validation rules", sitting next to "Techpacks") —
**not** a separate top-level module. That nav is collapsed/off-canvas by default: its links exist
in the DOM/`ariaSnapshot()` but aren't clickable until the header's own "Open navigation" toggle is
clicked first (see the Techpack QA's working notes).

Written from a live exploration against **uat.flooros.app** on 2026-09-30 (logged in as `alice`,

actually driven live this session; nothing has been run against dev or local yet (per this repo's

## Notes for whoever picks this up next

**Superseded 2026-10-01: this is now automated** (see the header and the 2026-10-01 automation
update at the bottom). The original doc-only note is kept below for history.

**The Advanced JSON schema, confirmed via real placeholder text (not guessed):** a rule's actual
logic lives in two JSON fields inside the collapsed "Advanced — rule JSON" group —
`Scope (JSON)` (optional; placeholder `{"op":"all","predicates":[]}`, meaning "applies to
everything" when left blank) and `Assertion (JSON) *` (**required**; placeholder
`{"kind":"itemPresent","itemCode":"HT1680"}`). This is the real gate on "Create rule"/"Save
changes" becoming enabled — Name and Description alone are not sufficient (TC:11). The "Describe
this rule" free-text box + "Generate" button is an AI-assist path presumably meant to fill Scope/
Assertion from a natural-language description instead of hand-writing JSON — **not exercised this
session** (Generate stayed disabled throughout since the fields we filled by hand already satisfied
the form; deliberately didn't test round-tripping through it, both to avoid an unnecessary AI-
backend dependency mid-exploration and because this repo has already documented the AI/copilot
backend as unreliable on uat elsewhere — see the Techpack QA's environment note' "AI Mode copilot
fails at Start extraction" section). Worth a dedicated, careful pass later.

**The version-bump-without-changes bug (TC:22) is real and still reproducing on the original rule
it was found on, but this session could NOT reproduce it on a rule created fresh — that's a
genuine, evidence-backed nuance, not a "confirmed fixed."** `EVERLANE-INTERLINING-COLOR-DARK` was
at Version 2 before the original 2026-09-29 repro, Version 3 immediately after (screenshots:
local exploration evidence (not committed)), and was already at **Version
5** by the start of this session (2026-09-30) — meaning something bumped it twice more in between,
without this repo's own scripts touching it. Cause unconfirmed (dev-team investigation? a
scheduled re-evaluation job? someone else editing it live?) — flagging the fact, not asserting a
cause, per this repo's own standing rule about not asserting causal claims without evidence. By
contrast, a rule created fresh this session (`PW EXPLORE 1790752869848`) correctly showed a
**disabled** Save-changes button with zero edits, both as a Draft and after Activating it — so
whatever the bug's real trigger is, it isn't simply "open a rule and click Save without typing
anything." **Per the user (2026-09-30): this has already been raised in ClickUp
([z941abxb4p](https://app.clickup.com/t/z941abxb4p)) and the dev team is actively working on
it** — no further root-causing needed from this side; re-check by re-running TC:22 once the dev
team confirms a fix, same pattern as this repo's AI Mode extraction-bug tracking. A plausible next
step for whoever picks this up in the meantime: reproduce on a rule that has
non-trivial pre-existing Scope/Assertion JSON (unlike this session's minimal
`{"kind":"itemPresent","itemCode":"PW-EXPLORE-TEST"}`) to see if a JSON-reserialization mismatch is
the real trigger — not confirmed, just the most plausible mechanism given the evidence so far.

**Two disposable rules were created and left behind by this session's live exploration — both
already archived, safe to ignore:** `01M3RK0MH0FFCHKJVSB52TYNAK` / "PW EXPLORE 1790752869848" and
`01M3RKCND4W02VEA9W5V70Q1BD` / "PW EXPLORE 1790753264031", both Version 1, both now Status =
Archived (confirmed — archiving is permanent, so these can't be cleaned up any further; they'll
just sit in the Archived tab indefinitely). The first was briefly **Active** and **global**
(applies to every customer) with a fabricated `itemPresent` assertion — flagged and archived
promptly since an Active global rule referencing a nonexistent item code could otherwise have
started surfacing false validation failures against real techpacks. Don't mistake either for real
seed data if they turn up in a future list query, same pattern as this repo's existing disposable-
techpack precedent (`TP202609-000008`, noted in the Techpack QA's working notes).

**Not covered this session, worth a follow-up pass:** actually clicking a status tab to confirm it
filters the grid (TC:5); clicking a sort button to confirm real re-ordering, not just its presence
(TC:8); exercising pagination (Next/Last page, changing rows-per-page) beyond confirming the
controls render (TC:9); whether the filter box matches on Description text specifically (only
Id/Name substrings were tried); duplicate-Name handling on Create; what happens to a rule that's
Disabled (TC:25); and the "Suggested" status's real origin (TC:27).
