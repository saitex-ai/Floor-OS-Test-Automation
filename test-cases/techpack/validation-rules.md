# Techpack — Validation Rules

- **User Story:** As a Techpack admin, I want to define and manage validation rules — global or
  scoped to a specific Customer — that automatically check techpack submissions against required
  attributes (labels, hangtags, interlining colour, trims, etc.) at a given Severity, so
  customer-specific compliance requirements are enforced before a techpack is approved.

## Notes for whoever picks this up next

**The Advanced JSON schema, confirmed via real placeholder text (not guessed):** a rule's actual
logic lives in two JSON fields inside the collapsed "Advanced — rule JSON" group —
`Scope (JSON)` (optional; placeholder `{"op":"all","predicates":[]}`, meaning "applies to
everything" when left blank) and `Assertion (JSON) *` (**required**; placeholder
`{"kind":"itemPresent","itemCode":"HT1680"}`). This is the real gate on "Create rule"/"Save
changes" becoming enabled — Name and Description alone are not sufficient (TC:11). The "Describe
this rule" free-text box + "Generate" button is an AI-assist path presumably meant to fill Scope/
Assertion from a natural-language description instead of hand-writing JSON — **not exercised this
session** (Generate stayed disabled throughout since the fields we filled by hand already satisfied
the form; deliberately didn't test round-tripping through it, both to avoid an unnecessary AI-
backend dependency mid-exploration and because this repo has already documented the AI/copilot
backend as unreliable on uat elsewhere — see the Techpack QA's environment note' "AI Mode copilot
fails at Start extraction" section). Worth a dedicated, careful pass later.

**The version-bump-without-changes bug (TC:22) is real and still reproducing on the original rule
it was found on, but this session could NOT reproduce it on a rule created fresh — that's a
genuine, evidence-backed nuance, not a "confirmed fixed."** `EVERLANE-INTERLINING-COLOR-DARK` was
at Version 2 before the original 2026-09-29 repro, Version 3 immediately after (screenshots:
local exploration evidence (not committed)), and was already at **Version
5** by the start of this session (2026-09-30) — meaning something bumped it twice more in between,
without this repo's own scripts touching it. Cause unconfirmed (dev-team investigation? a
scheduled re-evaluation job? someone else editing it live?) — flagging the fact, not asserting a
cause, per this repo's own standing rule about not asserting causal claims without evidence. By
contrast, a rule created fresh this session (`PW EXPLORE 1790752869848`) correctly showed a
**disabled** Save-changes button with zero edits, both as a Draft and after Activating it — so
whatever the bug's real trigger is, it isn't simply "open a rule and click Save without typing
